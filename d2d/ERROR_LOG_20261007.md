## E1 INA3221 金标写错方向：文档说可写的保留位被我编成只读

**逐字日志**（`d2d/eval/results_gen_ina3221kt.json` 的 tail 字段，5/12 份同型）

```
AssertionError: CRIT1.UNUSED[2:0] 是 RW 寄存器内的 RO 位：写全 1 后读回 7，期望复位值 0（整寄存器 0xffff）
```

**手册原文**（PDF p.31–32，Table 8-18/8-25 等）

```
15-3  C1L12-0   R/W  FFFh   Channel-1 critical-alert-limit data
bits 2-0  Reserved   R/W  0h   Reserved
```

**根因**：我按"名字叫 Reserved 就应当硬连 0"编码，但这 6 个告警限值寄存器的 Type 列是 **R/W**（B 档）。模型实现成可写是照手册做对的，被我的判据判红。

**修法**：IR 中 `CRIT1/2/3`、`WARN1/2/3` 的 `UNUSED[2:0]` → `access: "RW"`、`tier: "B"`，附页码证据；参考实现 `WRITE_MASK[0x07..0x0C]` 由 `0xFFF8` → `0xFFFF`。重过准入门：`4 passed, 4 skipped`，两探针仍咬人。

**影响面**：INA3221 的 ④ 失败数会下降（离线重评即可修正，**不需要重跑 GPU**）。同一颗里 `SHUNT_SUM_LIMIT`/`PV_UPPER`/`PV_LOWER` 的 Reserved 位手册写的是 `R 0h`（A 档），编码保持不变——**同一颗芯片内 A/B 并存**，所以任何"看名字判档"的做法都不成立。

## E2 保留位分类器过匹配：A 档被当成 Q0 约定位

**现象**（作废那一版对照，`_out/table12.log`）

```
TMP126    绿 0/12  54.2%   绿 3/12  70.8%   绿 3/12  72.9%   保留位被当可写存储 11/12   7 段
```

**根因**：`is_convention_bit()` 用位段名/描述正则（`UNUSED|RESERVED|恒 0|R-0`）判"是否未文档化保留位"，而**文档明说读 0 的 A 档**同样命中。TMP126 的 7 段在手册里逐位给了 Type：

```
p.29  15:9  Reserved   R   00h
p.30  15:5  Reserved   R   000h
p.26  1:0   Reserved   R   00b   These two bits will always read 00b
```

**影响面**：若不修，④b（约定敏感）会虚增——TMP126 一颗就贡献假的 +16.6pp、3 份凭空翻绿。

**修法**：IR 增加显式 `tier` 字段（A/B/C/UNVERIFIED，脚本 `_setup/tier_stamp.py`）；`is_convention_bit` 改为 **tier 优先**：A/B 永不参与翻转，只有 C 与 UNVERIFIED 进变体。

## E3 白送通过：ADS1220 没有任何 RO 对象却拿满 ③ 的分

**逐字日志**（`_out/table13.log` / `main_table.json` 的 `vacuous_excluded`）

```
!! 白送通过（已从分母剔除）：[{"chip": "ADS1220", "test": "test_readonly_protection",
   "passed_for_free": 12, "why": "IR 未声明该结构，harness 不 skip ⇒ 白送通过，已从分母剔除"}]
```

**根因**：harness 的 ③ 在"该寄存器没有 RO 位"时不 `pytest.skip`，而是空循环通过；正对照芯片（纯寄存器堆）因此白得 12 次通过，抬高 ③ 分母、压低 ③ 失败率。

**影响面**：③ 从旧口径 41.7%（8 颗、含白送）修正为 **46.2%（11 颗，剔除白送）**。

**修法**：`_setup/main_table.py` 用 junitxml 逐断言计 `passed/applicable`，并用 `declared(ir, test)==0` 把白送项剔出分母、单列 `vacuous_excluded`。harness 本身的 skip 条件留待窗口结束后改（会动历史分母，必须配合离线重评）。

## E4 参考实现掩码算错（被准入门当场抓住）

**逐字日志**

```
① 金标回归: False | 1 failed, 3 passed, 4 skipped in 0.14s
E   AssertionError: CTRL2.CS_PU_DISC[4] 写全 1 后读回 0，期望 1（整寄存器 0x4）
    assert 0 == 1
```

**根因**：CTRL2 可写位是 bit7/4/3/2/1/0（排除 bit6 自清零、bit5 文档要求保持 0），掩码应为 `0xBF`；我写成 `0xAF`（`1010_1111`）——漏 bit4、多 bit5，两头都错。

**修法**：改 `0xBF` 后 `4 passed, 4 skipped`。

**意义**：这是准入门（金标自回归 + 行为探针）第三次在 GPU 之前抓住金标侧的错。成本对比：本地回归 0.03 秒 vs 一颗 k-trial 10–19 分钟。

## E5 ④ 三桶公式标签写反

**错误版**（我第一次写进 `main_table.py` 的）

```python
"4b_confirmed_convention_fail": f4c - f4r,     # 实际是 ④u
"4u_unverified_fail": f4s - f4c,               # 实际是 ④b
```

**发现方式**：跑完看到 `④b 0 / ④u 39` 与"7 个确认 C 档位段"的事实矛盾（C 档应当有杠杆），反查公式。

**正确语义**：`④a = relax_cu 失败`；`④b = strict − relaxc`（只翻 C 就能消掉）；`④u = relaxc − relax_cu`（再翻 UNVERIFIED 才多消掉）。

**修正后**（`d2d/eval/main_table.json`，19:14）

```
strict 110/144 = 76.4%  →  ④a 71 (49.3%)   ④b 39 (27.1%)   ④u 0 (0.0%)
relaxc = relax_cu = 71   tier 计数 {'C': 7, 'UNVERIFIED': 3}
```

**副产品结论**：39 份**全部**由 7 个确认 C 档位段消掉，3 个 UNVERIFIED 段零影响 ⇒ 剩余人眼队列只是证据完整性问题，不改数字（唯一例外见"待决"）。

## E6 长跑进程内存里是旧代码，误杀正对照

**逐字日志**（`_out/chain.log:101`）

```
[14:57:05] ADS1220 反向对照失败 {'naive_regfile': False, 'reset_shift': True} → 不许上机

**根因**：链 #1 于 13:42 启动，`perturbation_control` 在 14:47 才修成"期望值按 IR 声明推导"。Python 模块在进程启动时加载，**磁盘改了内存没改**；ADS1220 不声明任何受保护位，naive 探针本就应该绿，旧代码无条件判红。

**防复发**：改判据代码后必须重启编排器；实例重启后旧编排器握的是死 SSH 传输，也要整条重启（今天 16:44 回收后就是这种情况，19:04 我按显式 PID 停掉三条旧链）。

## E8 并发竞态：两个批处理同时写同一批文件

**现象**：`rescore_variant` 与 `main_table` 各有一份在跑（16:52 启的 run#1 与 16:57 启的 run#2），同时写 `d2d/ir/<part>_variant_*_ir.json` 与 `main_table.json`。

**根因**：我重启动任务前没查 in-flight——正是我自己写进 memory 的那条 guardrail。

**危险度评估**：失败模式是"读到半截 IR → `json.load` 抛错"，属于**响的**、不是静默错；但仍会产出半截产物。

**修法**：按显式 PID 停掉 run#1 的重复 `main_table`（44556），保留修正版 rescore；新增 `_setup/joblock.py`（锁文件存 PID，活进程 → `exit 3` 拒启，死锁自动接管），`main_table` 已接。实测：

```
